# 为什么 Linux 不给预编译二进制

两条路都试过，各有硬伤。

## glibc 版会挑发行版

glibc 的符号是版本化的。在 Ubuntu 24.04 上编译出来的二进制，链接的是 `GLIBC_2.39` 这一代的符号。拿到 Debian 11 或 CentOS 7 上跑，会直接报下面这个。

```
version 'GLIBC_2.38' not found
```

根本起不来。

要覆盖还在服役的发行版，得在最老的环境里构建。常见做法是用 `debian:bullseye` 或 `ubuntu:20.04` 容器跑编译，产物才能下探。这么做还有个附带要求。构建时链接的每个库都得是那个老环境里的版本，否则又带出新依赖。

这条路能走通，但要为每个目标发行版验一遍，长期维护成本不低。

## musl 静态版会废掉 dlopen

看起来这是个好方案。全静态 musl 编译出来是真正的单文件，任何 Linux 内核都能跑，不依赖目标机装了什么 libc。

问题在 `dlopen`。静态链接后它不可用。

Lua 的 `require` 加载 C 扩展（`lfs`、`luasocket`、`lpeg`、`lua-cjson`）走的正是 `dlopen`。静态版会把这批库全部废掉，用户只能写纯 Lua 代码。

这个代价比它听起来大。用 Lua 的人里很大一部分就是为了那几个 C 扩展，去掉之后等于换了一门语言。

## 取舍

摆在一起看就清楚了。

| 方案 | 可移植性 | C 扩展 |
|---|---|---|
| glibc 动态 | 挑发行版 | 可用 |
| musl 全静态 | 到处能跑 | 全部失效 |
| 现场编译 | 完全匹配 | 可用 |

前两个各缺一半。第三个什么都有，代价是用户得等三十秒。

考虑到编译只需要 `gcc` 和 `make`，多数 Linux 用户的机器上本来就有（或者一条包管理命令的事），把这个选择权交给用户比替他决定更诚实。

## 脚本做了什么

`scripts/build-linux.sh` 干这几件事。

检查 `cc`、`gcc`、`clang` 哪个可用，检查 `make`，检查下载工具。

下载官方 tarball，打印 sha256 方便核对。如果本地已经有源码包，用 `LUABIN_LOCAL_SRC` 指定路径就跳过下载，内网和离线环境能走这条。

编译时探测 readline。探针是实际编译一个最小程序并链接 `-lreadline`，不是只看头文件。有就用 `linux-readline` 目标（交互模式带行编辑和命令历史），没有就降级到 `linux`。

装到 `~/.local`，可用 `PREFIX` 改。装完打印验证结果和 PATH 配置提示。

跑一遍大概三十秒。
